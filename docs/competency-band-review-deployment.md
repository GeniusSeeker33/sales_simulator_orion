# Human-approved competency-band reviews — Issue #22

Related to GeniusSeeker33/geniusseeker-talent-success-platform#22. No migration or production deployment has been performed.

## Decision and authorization contract

- A review is one human decision for one exact learner binding/person/employment episode and one `orion-sales/0.1-draft` competency C01–C15. The reviewer explicitly selects `B1`–`B5` or `defer` and writes a rationale. There is no default band, average, attempt-count threshold, aggregate competency profile or L1–L5 decision. The UI links the pinned model's behavioral anchors; pilot use of the draft still requires leadership approval.
- `learner_band.reviews` persists UUID, server-derived learner/reviewer identity, author scope, source environment/project, competency/version, outcome, minimized evidence references, rationale, reviewed_at, completed status, recorded timestamp, revision, predecessor, reason and request hash. `completed` means the review was published, including a defer; it does not mean competency achieved. `defer` means insufficient evidence and assigns no band. It neither resets nor carries forward another review's band.
- Public invoker RPCs `publish_competency_band_review(p_id, p_scope, p_body)` and `read_competency_band_reviews(p_scope, p_before, p_before_id)` call private implementations with empty search paths and explicit grants. Private table RLS is enabled; authenticated users have **no direct table reads or writes**. The existing authorization helper checks the authenticated subject and current approved/unrevoked/unexpired exact reviewer scope on every request. Writes require an active, separate learner binding. Scope/binding locks serialize publication against revocation. No email/name role inference, shared credentials or browser service-role key.
- Learner self-reads resolve only the current verified episode. Assigned reviewers may read only the explicit episode scope; historical retired-episode reads require a still-approved explicit historical scope and cannot publish/correct. Rehire creates separate history; no bands transfer by person matching.

## Evidence and correction rules

`p_body` accepts only `competency_version`, `competency_code`, `outcome`, `evidence` (array of `{id, revision}`), `rationale`, `reviewed_at`, optional `supersedes_id` and `correction_reason`.

- Evidence must be current, non-superseded **human-reviewed competency evidence**, exact revision, same binding/competency/version. Direct attempt/simulation/coaching IDs are rejected. AI can contribute only through that earlier human review. Duplicate references are rejected; 50 references is a request-size bound, not a proficiency threshold. Zero references is allowed only for defer.
- Publication locks source rows in deterministic ID order using the same lock mode as evidence correction, then checks revisions/successors. No raw source content is copied: store only evidence UUID/revision, finding/source-type snapshot and system/entity/environment/project context. Narrative, raw AI feedback, recordings, transcripts and private artifacts stay out. The rationale is new learner-visible reviewer judgment, not copied source material.
- Technical failure, disputed and insufficient opportunity are non-scored context. An all-non-scored or empty body permits only defer; an actual band requires substantive human-reviewed support/non-support evidence. This is a sufficiency safeguard, **not a band calculation**. With substantive evidence the human still explicitly chooses a band or defers and explains the decision; no automated decrement is applied for non-scored context.
- Correction requires original reviewer, active exact-episode scope, same competency/version, latest predecessor and a reason. It appends a new UUID/revision and uniquely supersedes the original. Update/delete triggers prohibit silent rewriting. Other reviewers can publish independent attributable reviews but cannot overwrite another's. This is review history, not a rule selecting a single canonical current band from competing reviews.
- Source evidence corrected later does not mutate the prior decision. Read responses flag the source successor; the reviewer must reconsider and publish a correction with current references. Identical UUID/body retries return the existing receipt only after renewed authorization. They do not create a new decision or revalidate an already-published historical receipt as if it were a fresh review.
- Existing durable attribution, learner/reviewer practice and coaching history, competency evidence and legacy browser quarantine are unchanged. No progression, employment-action, integration or compensation state is written. UI keeps drafts in memory only and rechecks access on refresh/focus/30-second poll; every server request is authorized independently. Revocation cannot erase information already delivered to a client.

## Verification

`npm run test:learner` runs all five actual migrations in isolated PGlite PostgreSQL using authenticated/anonymous roles and synthetic JWT subjects. Coverage includes scoped publish/read, outside/revoked/expired denial, exact same competency/version, stale/superseded/wrong-episode references, no direct AI sources, mandatory rationale/outcome, defer/non-scored handling, own-learner read-only, immutable correction lineage, disk restart, pagination, rehire and unchanged aggregate-band/L1 sentinels. Prior practice/coaching/evidence/legacy regression suites also run. No hosted database was contacted; PGlite does not validate the Supabase JWT gateway/PostgREST, browser interaction or multi-connection concurrency.

Manual staging acceptance:

1. Reviewer opens **Assigned Learner History**, chooses A's exact episode, reads the human-reviewed competency evidence and opens **Review one competency**. Select the same competency, enter evidence UUID + revision per line, explicitly choose a band and supply rationale. Refresh/new authenticated session retrieves the same decision. Verify empty outcome and missing rationale are rejected; nothing computes or recommends a band.
2. Defer with no evidence or only technical-failure/disputed/insufficient-opportunity evidence. Confirm “no band assigned.” Those references alone cannot publish B1–B5. With substantive evidence, the review still requires human choice/rationale and does not average or infer any band.
3. Try another competency/version, learner episode, raw practice ID, stale revision or superseded evidence. All fail. Correct source evidence; existing review keeps its original outcome/reference and flags successor. Correct the review using current evidence and a reason; original reviewer/decision/history remain visible.
4. Learner A opens **My Coaching** and sees band, rationale, reviewer, references, timestamps and correction lineage but no edit controls. B and outside reviewer cannot read A via UI or direct RPC. Revoke/expire the reviewer scope and retry using the same JWT, including pagination and write retry; future reads/writes fail.
5. Retire the old learner binding and provision a separate rehire episode. New self-history is empty; old reviews are neither inherited nor writable. Only an explicitly approved old-episode scope can read prior reviews. New-episode publication rejects old evidence and old-review corrections.
6. From separate staging connections, race source evidence correction against publication, and scope/binding revocation against publication. Verify serialized outcomes; no new decision may rely on supersession/revocation committed before it obtained the relevant lock. A completed request before revocation remains legitimate history. Confirm no L1–L5, compensation or employee-action writes occur.

Release decisions remaining: pilot approval for draft anchors, reviewer scope ownership/expiry, retention/access policy, unavailable-original-reviewer escalation and handling independent conflicting reviews. These do not authorize aggregation, progression or employment actions.
